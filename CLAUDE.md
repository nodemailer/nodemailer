# Nodemailer

E-mail sending library for Node.js. Zero runtime dependencies. Written in TypeScript under `src/` and published as a dual package: ES modules in `dist/esm/` and CommonJS in `dist/cjs/`, each with its own type declarations. Entry point is `src/nodemailer.ts`, which exposes `createTransport(transporter, defaults)` and routes to one of the bundled transports based on the options object.

## Layout

- `src/nodemailer.ts` — public entry, transport dispatch (`createTransport`), `createTestAccount`, `getTestMessageUrl`. Named exports plus a default export object so both `import nodemailer from 'nodemailer'` and `import { createTransport } from 'nodemailer'` work.
- `src/mailer/` — `Mail` class: the user-facing transport wrapper that normalizes messages, runs the DKIM signer, and hands off to the underlying transport's `.send()`.
- `src/mail-composer/` + `src/mime-node/` — message → MIME tree → raw RFC822 stream.
- `src/smtp-connection/` — low-level SMTP/LMTP/ESMTP client. Hot path; security-sensitive. Used by `smtp-transport` and `smtp-pool`.
- `src/smtp-transport/` — single-shot SMTP transport.
- `src/smtp-pool/` — pooled SMTP transport with rate limiting.
- `src/sendmail-transport/`, `src/ses-transport/`, `src/stream-transport/`, `src/json-transport/` — alternate transports.
- `src/dkim/`, `src/addressparser/`, `src/mime-funcs/`, `src/base64/`, `src/qp/`, `src/punycode/`, `src/well-known/`, `src/xoauth2/`, `src/fetch/`, `src/shared/` — supporting modules.
- `src/package-info.ts` — generated by `scripts/build.js` from `package.json` (`name`, `version`, `homepage`). Gitignored and regenerated by `npm run build` and `npm run typecheck`. Never import `package.json` directly from `src/`.
- `scripts/build.js` — the build: generates `src/package-info.ts`, runs `tsc` with `tsconfig.esm.json` and `tsconfig.cjs.json`, writes a `package.json` with the module format into each output directory, and rewrites CommonJS modules that only have a default export so `require()` returns the class or function itself.
- `dist/` — build output, gitignored; it is what gets published to npm (`src/` is not part of the package).
- `test/` — mirrors `src/` structure, TypeScript, run with `node --import tsx --test`. Most suites spin up real `smtp-server` instances on ephemeral ports; raw `net` servers are used when byte-exact reply control is needed (e.g. injecting non-ASCII or invalid UTF-8). `test/package/package-test.ts` loads the built `dist/` output through the `exports` map the way an installed copy is loaded.

Each transport must implement `name`, `version`, and `send(mail, callback)`. `Mail` discovers them via duck typing.

## Engine target and module format

- `engines.node = ">=20.0.0"`. TypeScript `target: ES2022` with `lib: ES2023`. `@types/node` is pinned to the 20.x line so the compiler rejects APIs that do not exist on Node 20.
- Source uses ES module syntax and is compiled twice from the same files: `tsconfig.esm.json` (`module: nodenext`) into `dist/esm/` and `tsconfig.cjs.json` (`module: commonjs`) into `dist/cjs/`. Because every file must compile both ways, code under `src/` must not use `import.meta`, `require`, `module`, `exports`, `__dirname`, `__filename`, top-level `await`, or JSON imports.
- `erasableSyntaxOnly` is on: no enums, no namespaces with runtime code, no parameter properties, no decorators. Type-only namespaces are allowed.
- Relative imports always carry the `.js` extension and point at a file (`'../mime-node/index.js'`), never at a directory.
- Node builtins are imported with the `node:` prefix. Use a default import (`import net from 'node:net'`) when the whole module is used, so tests can still stub methods on it; use named imports otherwise. Do not use `import * as` for builtins.
- Tests are ES modules too (`.ts`, run through `tsx`). They may use `import.meta.url`; derive `__dirname` with `path.dirname(fileURLToPath(import.meta.url))` rather than `import.meta.dirname`.

## Export shapes

Deep imports such as `require('nodemailer/lib/mail-composer')` and `require('nodemailer/lib/smtp-connection')` are used in the wild and documented on nodemailer.com, so the CommonJS shapes are part of the public API:

- Modules that used to be `module.exports = Class` or `module.exports = function` have exactly one runtime export, `export default`. The build rewrites their CommonJS output so `require()` returns the class or function itself (a non-enumerable `.default` alias is kept for transpiled default imports). Such modules must not gain other runtime exports; extra values are attached as properties on the exported function (`nmfetch.Cookies`, `sign.relaxedHeaders`). Type exports are fine.
- Utility modules (`shared`, `shared/url`, `shared/objects`, `mime-funcs`, `mime-funcs/mime-types`, `base64`, `qp`, `punycode`, `errors`) use named exports only.
- `package.json` `exports` maps `.` and every `./lib/<module>` subpath (plus `./lib/*` patterns for files) to both builds. When adding a directory module under `src/`, add its `./lib/<name>` entry.

## Conventions

- Callback-first style throughout the public API. Many internals are still callback-based; match the style of the file you are editing rather than introducing promises mid-module.
- Every options object a class or function reads gets an exported interface in the same file, named after the module (`SMTPConnectionOptions`, `DKIMOptions`, `MailComposerOptions`). Only include fields the code actually reads. The root entry re-exports the public ones.
- Errors carry extra properties (`code`, `response`, `responseCode`, `command`, ...). Type them as `NodemailerError` from `src/errors.ts` and assign `err.code` from the constants exported there.
- Prettier handles formatting; ESLint with typescript-eslint handles correctness, and `npm run lint` also runs the type-check. Run `npm run format` and `npm run lint` before sending changes.
- camelCase for variables and methods, PascalCase for classes and types. Snake_case is not used.
- Prefer small, surgical diffs. The codebase is mature and load-bearing — avoid drive-by refactors, comment churn, or "improvements" outside the scope of the change.
- Every change to security-sensitive code (anything in `src/smtp-connection/`, address parsing, header generation, DKIM) needs tests that exercise the failure mode, not just the happy path.

## Testing

- `npm test` — builds first (`pretest`), then runs the full suite via `node --import tsx --test` against `src/` (~150s, 490+ tests, runs serially).
- `npm run test:coverage` — same suite under `c8`, source-mapped back to `src/`.
- `npm run lint` / `npm run lint:fix` — ESLint; `lint` also runs `npm run typecheck` (`tsc --noEmit` over `src/` and `test/`).
- `npm run build` — produce `dist/`.
- `npm run format` / `npm run format:check`.
- Single file: `node --import tsx --test test/mailer/mail-message-test.ts`.
- Test dependencies without type definitions are declared as `any` modules in `test/types/modules.d.ts`.

Always run `npm test` and `npm run lint` before considering a change done. Tests are required to pass on every commit because release-please cuts releases directly from `master`.

## Releases

Releases, version numbers, the `version` field in `package.json`, git tags, `CHANGELOG.md` entries, and npm publication are all managed automatically by the release-please GitHub Action (`.github/workflows/release.yaml`, configured by `.release-please-config.json`). **Never edit any of these manually and never propose manual edits to them.**

Release-please derives the next version and changelog from Conventional Commit messages on `master`, opens a release PR (`chore: release X.Y.Z [skip-ci]`), and publishes to npm with provenance when that PR is merged. The `prepare` script builds `dist/` on install and before publish, so build output is never committed. The only thing that should land on `master` between releases is normal commits with Conventional Commit prefixes — release-please takes care of the rest.

Conventional Commit prefixes used in this repo: `fix:`, `feat:`, `chore:`, `docs:`, `refactor:`, `test:`. Use `fix:` for anything users would benefit from seeing in the changelog, including security fixes (reference the GHSA in the body).

## Security

This is a widely-deployed library — security-sensitive changes get extra scrutiny:

- SMTP command injection: any user-controllable value that flows into a written SMTP command (envelope addresses, sizes, the `name`/EHLO option, headers) must be CRLF-stripped or rejected at the boundary. Sanitize at the assignment, not at every call site.
- Server reply parsing in `src/smtp-connection/index.ts` uses a `'binary'` byte-container intermediate to reassemble multi-byte UTF-8 across socket chunks; the actual decode happens at line boundaries via `decodeServerResponse`. Don't change the chunk-buffering encoding without understanding why.
- Reference the GHSA ID in commit messages for advisories.
